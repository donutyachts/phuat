UX-GLOB-01 — Modal action buttons use consistent labels/order/placement across create and edit modals

Module: Global · Heuristic: Consistency and standards · Required role: Any
Steps
Open New Sub User, New Ticket, and an Edit flow (e.g. edit a Team Contact). Compare button labels, order, and position.
Expected result
Primary action (Save/Create) and secondary action (Cancel/Close) use the same wording order and position across every modal.
Actual result
Compared button labels/order/placement across New ticket, Invite User, and Edit Team Contact: every modal uses a secondary action (Cancel) immediately left of a primary green action on the right (Create ticket / Send Invitation / Save contact).
Notes
Edit Team Contact also shows a red Delete button further to the left, separated from the Cancel/Save pair — a common, deliberate pattern for isolating destructive actions, not an inconsistency.
Pass

UX-GLOB-02 — Save/submit actions show a loading or in-progress state

Module: Global · Heuristic: Visibility of system status · Required role: Any
Steps
Trigger a save with a noticeable network delay (e.g. create Sub User submit a ticket reply) and observe the button/UI during the request.
Expected result
Button shows a busy/loading state between click and completion; UI does not appear frozen or allow duplicate submits.
Actual result
Clicking Create ticket while the form was valid showed a spinner icon inside the button and disabled the form fields until the request completed.
Notes
Note for testers: the button also LOOKS dimmed/disabled when a required field (Category) is missing, which can be mistaken for a loading state — worth a moment's care when reproducing this check.

UX-A11Y-01 — Primary flows are fully operable by keyboard alone

Module: Accessibility · Heuristic: WCAG 2.1 AA - Keyboard operability · Required role: Any
Steps
Using only Tab/Shift+Tab/Enter/Space/Escape (no mouse), open a creation modal, fill required fields, submit; also navigate a data table.
Expected result
Every interactive element is reachable and operable via keyboard, with a visible focus indicator at each step.
Actual result
Keyboard-only walkthrough of New ticket: Subject, Impacted account, Category, and Subcategory are all fully operable by Tab/Enter/Arrow keys with a visible focus ring — but Tab skips over the Description rich-text field entirely, landing directly on its Bold toolbar button instead. Typed text while that toolbar button is focused is silently discarded (never appears in the field).
Notes
FINDING: a keyboard-only user cannot enter a ticket Description at all via Tab navigation — the contenteditable area is missing from the tab order. Table row links ARE reachable and Enter-activatable (opened ticket #63 successfully), so the failure is isolated to the rich-text editor, not the whole flow.
Fail

UX-A11Y-02 — Form fields have visible associated labels and validation errors are shown as text near the field

Module: Accessibility · Heuristic: WCAG 2.1 AA - Labels and error identification · Required role: Any
Steps
Open a creation form and trigger a validation error (leave a required field blank submit).
Expected result
Each field has a persistent visible label (not placeholder-only); the error is shown as text near the field, not conveyed by color/border alone.
Actual result
Every field observed (Email, Subject, Category, etc.) has a persistent visible label, not placeholder-only. Submitting Invite User with a blank Email produced a toast reading 'The email field is required.' — but submitting with a malformed email (no @) produced no visible error at all (no toast, no inline text, no red border).
Notes
FINDING: required-field errors surface as a global toast rather than text near the field itself, and format-invalid input fails silently with zero feedback — a screen reader user or anyone who missed the toast has no way to know why the form didn't submit.
